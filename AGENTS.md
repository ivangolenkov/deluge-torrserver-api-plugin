# Deluge Stream Plugin: руководство для AI-агентов

## О проекте

Deluge Stream Plugin — самостоятельный Python-плагин для Deluge. Он предоставляет TorrServer-совместимое воспроизведение для Lampa/Num, временные и постоянные торренты с FIFO-очисткой, streaming QoS и скачивание готовых файлов/ZIP через стандартный Web UI Deluge.

Стек: Python, Twisted, существующая сессия libtorrent в deluged, SQLite WAL; клиентская часть расширяет штатный Web UI Deluge. Целевые платформы — Linux x86_64 и ARM64, включая NAS/Docker. Точные поддерживаемые версии определяются проверками фазы 0.

Главный продуктовый контракт — [SPEC.md](SPEC.md). Описание для пользователей — [README.md](README.md). Последовательность реализации и статус — [tasks/README.md](tasks/README.md).

## 1. Источники требований и область работы

1. Выполнять прямые указания пользователя в пределах уже согласованной задачи.
2. Читать SPEC.md, файл текущей фазы и отчёт предыдущей фазы до изменений.
3. При противоречии плана и ТЗ явно выявить его. Не менять согласованные требования ради упрощения реализации; сначала подготовить обоснованный вариант изменения.
4. Фазы уточняют ТЗ, но не объявляют выполненные функции без кода и проверок. Технические решения по умолчанию можно уточнять с записью причины, сохраняя продуктовый объём.
5. Не переносить в проект стек, команды и ограничения Torrent-Stream-Hub механически: здесь нет Go, Vue и собственного торрент-движка.

## 2. Работа по фазам

Разработка разделена на шесть последовательных фаз: 0–5. Каждый файл tasks/phaseN-*.md содержит цель, зависимости, задачи, проверки и Definition of Done.

- Начинать реализацию фазы по команде пользователя или в пределах уже разрешённой последовательности фаз.
- Если пользователь разрешил несколько фаз или весь план, продолжать после выполнения промежуточных DoD; повторно разрешение на уже согласованную работу не запрашивать.
- Не переходить к следующей фазе, пока текущая не завершена и не проверена. Исключение — явно согласованное изменение плана, отражённое в документах.
- До начала обозначить конкретный план и текущий статус. Выполнять необходимую обратимую работу самостоятельно в согласованных границах.
- Существенные новые требования сначала сопоставить с SPEC.md и фазами, затем внести изменения в план; не оставлять документацию противоречащей реализации.
- Не смешивать запрос на планирование с реализацией будущих фаз. Наличие планов, README и шаблонов не означает завершение фазы 0.

Статусы фаз: «Не начата», «В работе», «Заблокирована», «Завершена». Блокировка означает конкретное препятствие, а не просто отсутствие готовности. Отмечать завершение только после фактического выполнения DoD.

## 3. Обязательная отчётность

После каждой фазы или значимой части обновлять tasks/implementation/phaseN-report.md. Формат описан в [tasks/implementation/README.md](tasks/implementation/README.md), заготовка — [report-template.md](tasks/implementation/report-template.md).

Отчёт должен содержать:

1. Реализованное поведение и созданные/изменённые файлы.
2. Исходный DoD с фактическими отметками и подтверждением каждого выполненного пункта.
3. Точные команды проверок, среду, версии и результаты; причины пропущенных проверок.
4. Результаты сценариев A01–A26 из ТЗ, относящихся к фазе, с указанием проверенной части.
5. Изменения README, Makefile и CI/CD или обоснование, почему они не потребовались.
6. Отклонения от плана, оставшиеся ограничения, незавершённые задачи и следующий шаг.

Не создавать фиктивные успешные отчёты заранее. Не приравнивать mock-тест к проверке настоящего Deluge, сборку к проверке установки, локальный запуск к успешному GitHub Actions run, а анализ исходников — к runtime-проверке.

## 4. Технические инварианты

- Вся серверная функциональность работает внутри core-плагина Deluge. Без отдельного Go-сервиса, второй libtorrent session, форка или обязательного monkey patch Deluge/libtorrent.
- Добавление/удаление выполнять через Deluge. Доступ к handle, EventManager и AlertManager изолировать адаптером. Не вычитывать общую очередь alerts самостоятельно.
- Не блокировать Twisted reactor сетевым ожиданием, SQLite, файловым вводом-выводом и ZIP. Worker-очереди и буферы должны иметь пределы и отмену.
- SQLite — единственная БД плагина; WAL, busy timeout, миграции, ограниченные соединения и корректная потоковая модель обязательны.
- Готовность данных определяет Deluge/libtorrent. Не считать размер файла, sparse-области или исторический прогресс доказательством наличия байтов.
- Временный торрент сохраняется после штатного рестарта deluged. По согласованному упрощению явное отключение плагина сбрасывает временность, публикацию и экземплярные metadata/viewed; обычный stop/start daemon не делает этого. После crash временность/FIFO сохраняются, но прежняя публикация и автоочистка требуют явного подтверждения администратором. Постоянные и существовавшие до установки торренты не становятся временными неявно. Hardlinks для политики хранения не обязательны.
- Автоочистка запускается только из-за превышения количества временных торрентов. Не добавлять удаление по размеру, TTL или свободному месту.
- FIFO не пропускает защищённого старейшего кандидата. Playback, preload, download, ZIP, ticket-reservation и debounce защищают от автоочистки.
- Смена политики, начало передачи и удаление должны быть согласованы. Идентичность экземпляра защищает от callbacks старого торрента после delete/re-add того же hash.
- QoS агрегирует deadlines нужных pieces нескольких сессий и не меняет пользовательские file priorities/skip/first-last/pause/queue. По согласованию остаточные native piece priorities после просмотра/crash допустимы: не нужен собственный recovery journal или восстановление piece vector. Готовые проверенные данные читаются даже на паузе/skipped; payload/recheck/re-download остаются Deluge/libtorrent.
- «Стриминг» в UI — наблюдаемая playback-активность, отдельно от preload, обычного скачивания и ZIP. Не подписывать число HTTP-запросов как точное число людей.
- Из Web UI скачиваются только готовые файлы; весь ZIP доступен только при готовности всех payload-файлов, включая skipped. ZIP64 формируется потоково без второго полного архива на диске.
- CORS * нужен TorrServer-совместимым маршрутам. Он не отменяет авторизацию RPC и download tickets и не разрешает выдачу чужих данных.
- Не удалять общий каталог загрузок или чужие payload-файлы. При неоднозначном владении отклонить опасную операцию с диагностикой.
- Для удаления согласованы штатные гарантии Deluge/libtorrent: preflight известных shared/unsafe paths и matching native completion/failure alerts, без дополнительной гарантии неизменности путей против внешних queued rename/move/re-add. Не требовать filesystem barrier или собственного unlink ради усиления этого контракта. После crash сохранённый manifest используется только для read-only проверки; неоднозначность остаётся ручной.

## 5. Тестирование и Makefile

Makefile обязателен начиная с фазы 0. Он является единым входом в основные сценарии локальной работы и CI, а не набором команд, печатающих обещания.

Контракт целей, момент их появления и состав проверок указаны в [tasks/README.md](tasks/README.md). Базовый набор: help, bootstrap, lint, format-check, check-docs, test-unit, test-integration, test, build, smoke, check, clean. Позже добавляются проверки Web UI/downloads, Docker и release-check.

- make help — безопасная цель по умолчанию с описанием команд и зависимостей.
- make check — обязательные актуальные проверки, сборка и smoke; новая функциональность расширяет общий набор.
- CI вызывает те же make-цели; существенная логика сборки не дублируется в YAML.
- Отсутствие обязательной зависимости не маскируется успешным skip. Сообщить, как подготовить окружение.
- make clean удаляет только генерируемые файлы проекта, никогда пользовательские downloads, профиль Deluge или SQLite.
- make build и make check не устанавливают плагин в пользовательский Deluge и не публикуют его.

Для бизнес-логики писать unit-тесты. Для persistence — интеграционные тесты с временной SQLite. Для lifecycle, reads, QoS, packaging — проверки с настоящим Deluge/libtorrent, локальным seed и изолированным профилем. Для UI — проверки статусов/действий и документированные пользовательские сценарии.

Не использовать публичный swarm как обязательную основу CI. Гонки проверять управляемыми сценариями и fault injection. Проверять относящиеся к изменению риски; после успешных обязательных проверок не повторять весь набор без новых причин.

## 6. README и документация для человека

README.md обязателен и обновляется вместе с изменением поведения, команд и поставки. Писать по-русски понятным языком; отделять готовые возможности от плана.

К выпуску README должен объяснять:

- Что делает проект, кому он нужен и какие ограничения имеет.
- Поддерживаемые Linux/Python/Deluge/libtorrent и выбор подходящего plugin artifact.
- Установку в deluged и в отдельный deluge-web, включение и первичную настройку.
- Подключение Lampa/Num, HTTP-порт, public_base_url, публикацию торрентов и работу Web UI.
- Сборку из чистой копии, зависимости и команды Makefile, запуск тестов.
- Docker Compose, постоянные volumes и права доступа.
- FIFO, последствия временного статуса, состояние стриминга, готовность файла/ZIP.
- Обновление, отключение, backup/restore, диагностику и получение релизных artifacts.

Проверять команды на чистом изолированном окружении. Пока код или релиз отсутствует, явно указывать это; не выдавать планируемые команды установки/сборки за работающие и не ссылаться на несуществующие готовые релизы.

## 7. GitHub Actions и выпуск

- Фаза 1 создаёт .github/workflows/checks.yml для проверки PR/push, сборки и smoke-установки. Дальнейшие фазы расширяют его реальными тестами.
- Фаза 5 создаёт .github/workflows/release.yml для автоматической сборки и публикации плагина в GitHub Releases по версии/тегу после обязательных проверок того же commit.
- PR/branch runs не публикуют релизы. Ручная проверка workflow поддерживает запуск без публикации.
- Публиковать именно проверенные artifacts с версией, checksum и описанием совместимости; не объявлять произвольный wheel устанавливаемым Deluge-плагином без smoke-проверки.
- Не перезаписывать выпущенные assets другим содержимым. Повторный запуск должен быть предсказуемым и проверять совпадение версии/содержимого.
- Подготовка workflow не означает разрешение создать/отправить релизный тег или опубликовать релиз сейчас. Реальный выпуск выполняется в рамках отдельной команды пользователя либо уже явно разрешённого релизного процесса.
