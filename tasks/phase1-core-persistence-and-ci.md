# Фаза 1: каркас плагина, persistence, lifecycle и CI

Статус: **Не начата**.

Предпосылка: завершена [фаза 0](phase0-feasibility-and-tooling.md), прочитан её отчёт. Основание: [SPEC.md](../SPEC.md), §§2–4, 9–13. Отчёт: tasks/implementation/phase1-report.md.

## Цель

Превратить проверенный прототип в поддерживаемый каркас core/web-плагина с SQLite, управлением политикой хранения и автоматическими проверками GitHub Actions. Автоматическое удаление и полноценный streaming ещё не включаются.

## Задачи

### 1. Структура и адаптер

- Оформить production package, core/web entry points, версию, данные Web UI и схему конфигурации.
- Изолировать Deluge/libtorrent в адаптере: операции с торрентами, события, status fields, alert handlers и проверки runtime.
- Ввести record_id/идентичность экземпляра и защиту от поздних callbacks после удаления и повторного add.
- Реализовать согласованный enable/disable, очистку частично созданных ресурсов и отсутствие дублирующихся handlers/listeners.
- Подготовить RPC с явной проверкой owner/admin и совместимости core/web-версий; не отдавать бинарные payload-данные через RPC.

### 2. SQLite и политика

- Создать миграции и repository для torrent_policy, metadata, settings, viewed и журнала операций. Persistence viewed подтверждён reference-fixtures фазы 0: set/list/rem, привязка к файлу и экземпляру; HTTP handlers остаются задачей фазы 3.
- Настроить WAL, busy timeout, ограниченные соединения и неблокирующее reactor выполнение.
- Реализовать переключение временный/постоянный, опубликованный/неопубликованный и монотонный FIFO-ключ без запуска удаления.
- Постоянный → временный получает новый ключ; повторная установка состояния идемпотентна. Обычные/существующие торренты остаются постоянными.
- Реализовать правила повторного add и aliases, не создавая второго торрента для того же содержимого.
- Согласовать restart с каталогом Deluge: сохранять политику, удалять устаревшие связи без воскрешения торрента, не выводить временность из отсутствующей записи.
- Определить recoverable порядок изменений между Deluge и SQLite; никакой фиктивной общей транзакции.

### 3. Начальная web-интеграция и конфигурация

- Загружать web-часть штатным механизмом и проверять доступность core-части.
- Зарегистрировать необходимые status fields и RPC, которыми позднее воспользуется UI фазы 4.
- Валидировать настройки до применения, включая max_temporary_torrents и контекст владельца listener.
- Если core недоступен, Web UI Deluge продолжает работать с понятной диагностикой функций плагина.

### 4. GitHub Actions checks

- Создать .github/workflows/checks.yml: pull_request, push в основную ветку, workflow_dispatch и reusable workflow_call для будущего релиза.
- Использовать закреплённый runtime фазы 0 и вызывать Makefile вместо копии build/test-команд в YAML.
- Выполнять make check, установку/enable/disable собранного artifact в чистом профиле и сохранять artifacts/логи при ошибках.
- Начать с подтверждённой Linux-среды; явно описать, какие части ARM64-матрицы автоматизированы уже сейчас и что будет завершено в фазе 5.
- PR/branch runs не создают релиз и не требуют публикационных секретов. Использовать минимальные permissions; версия action фиксируется воспроизводимо.
- Документировать triggers, имя обязательной проверки, получение artifacts и ручной запуск. Фактический hosted run проверяется при наличии GitHub-репозитория.

### 5. Makefile и документация

- Сохранить make-интерфейс фазы 0 и включить новые unit/integration/lifecycle проверки в test/check.
- Проверить, что build включает core/web entry points, scripts и metadata, а smoke тестирует artifact, а не импорт исходников из checkout.
- Дополнить README рабочей установкой/отключением core/web частей, настройками и проверенными make-командами.
- Добавить описание текущего CI и честно указать, что публикация релизов появится в фазе 5.

## Проверки

Обязательны make check; временная SQLite с миграцией/ошибкой/повторным открытием; реальный Deluge restart, delete/re-add и 20 enable/disable; core/web в отдельных процессах. Начальное покрытие A01, A11–A12, A14–A15, A23–A24.

Если удалённый репозиторий ещё не создан, проверить синтаксис workflow и эквивалентные локальные команды, а hosted run записать как внешнюю непроверенную часть. Не подменять этим факт успешного GitHub CI; проверка реального run обязательна до выпуска.

## Definition of Done

- [ ] Реализованы production package, адаптер, core/web entry points и корректный lifecycle.
- [ ] SQLite-модель и миграции сохраняют политику и не блокируют reactor.
- [ ] Переходы временности/публикации и aliases проверены; удаления по лимиту пока нет.
- [ ] Restart/reconciliation и защита от старых callbacks проверены с настоящим Deluge.
- [ ] RPC и status fields имеют необходимые проверки прав и экземпляра.
- [ ] Создан checks.yml с реальной сборкой, тестами и smoke через Makefile.
- [ ] CI не публикует релизы; artifacts пригодны для тестовой установки.
- [ ] make check проходит; статус hosted run указан достоверно.
- [ ] README содержит актуальные инструкции установки, сборки, тестов и CI.
- [ ] Отчёт и индекс фаз обновлены, незавершённые проверки перечислены.
