# Фаза 0: проверка реализуемости и инструменты разработки

Статус: **Не начата**.

Основание: [SPEC.md](../SPEC.md), §§3, 5–8, 13–15. Предыдущей фазы нет. Отчёт создаётся в tasks/implementation/phase0-report.md.

## Цель

На настоящем Deluge подтвердить ключевые возможности плагина без изменения клиента, выбрать поддерживаемый runtime и подготовить воспроизводимую сборку. Результат — минимальный устанавливаемый исследовательский плагин и проверенные решения, а не готовый TorrServer-продукт.

## Задачи

### 1. Матрица и изолированное окружение

- Зафиксировать точные версии Deluge 2.2.x, Python, libtorrent bindings, Twisted, setuptools и инструмента упаковки; начать с предложенного в ТЗ профиля.
- Проверить доступность и установку на Linux x86_64/ARM64. Записать, где выполнялись реальные архитектурные проверки, а где использовалась эмуляция.
- Подготовить тестовый профиль Deluge, временные каталоги, локальный seed и контролируемые torrent fixtures. Не использовать пользовательский профиль и публичный swarm.
- Зафиксировать лицензии используемых зависимостей и способ установки системных prerequisites без скрытого изменения глобального Python-окружения.

### 2. Реальный core-прототип

- Собрать пакет с core entry point, установить его штатным механизмом, проверить enable/disable и регистрацию RPC.
- Получить handle торрента из существующей сессии Deluge; проверить set/reset_piece_deadline, piece_priority при необходимости, read_piece/read_piece_alert.
- Проверить доступность и lifetime буфера Python alert. Получать события через общий AlertManager, не вычитывая session.pop_alerts самостоятельно.
- Открыть HTTP listener в deluged и отдать отменяемый диапазон незавершённого файла. Проверить отсутствие блокировки reactor и ограничение буферов.
- Подтвердить, что операции не требуют второго движка, форка или monkey patch Deluge/libtorrent.

### 3. Риски состояния и данных

- Измерить поведение при смене file priorities/first-last mode, ручной паузе, очереди, recheck, move и delete/re-add.
- Проверить временные overrides при save-resume, штатном shutdown, crash и повторном enable. Выбрать способ, не оставляющий streaming QoS постоянным.
- Проверить отображение v1/v2/hybrid hash aliases, payload-файлов и pieces, включая pad-файлы и общие граничные pieces.
- Проверить потоковый ZIP64 writer: файл >4 GiB, много записей, отсутствие полного архива в памяти/на диске, отмена клиента. Это технический эксперимент, не выпуск download-функции.
- Записать решения и ограничения в docs/architecture.md и docs/compatibility.md либо эквивалентные отдельные документы.

### 4. Клиентский контракт

- Зафиксировать версии/коммиты Lampa, Num и эталонного TorrServer.
- Собрать обезличенные fixtures: add, file list, preload/stat, Range/seek, cache, settings, viewed, закрытие страницы.
- Определить точные типы DTO, минимальный viewed-контракт и поведение ошибок. Не считать заглушки Torrent-Stream-Hub автоматически правильным эталоном.
- Сохранить fixtures и описание их получения. Если нет доступа к обязательному клиенту, отразить ограничение, а не закрывать DoD совместимости.

### 5. Makefile и README

- Создать работающий Makefile по контракту [tasks/README.md](README.md): help, bootstrap, lint, format-check, check-docs, test-unit, test-integration, test, build, smoke, check, clean.
- make build должен собирать настоящий устанавливаемый прототип; make smoke — проверять его в чистом профиле.
- Предусмотреть необходимые тесты для прототипа; make check не может успешно пропускать отсутствующую обязательную среду.
- Обновить README: точные проверенные prerequisites, путь от чистой копии к сборке и установке прототипа, место artifact и способы запуска тестов.
- Сохранить явное различие между прототипом и будущими продуктовым возможностями. Не объявлять готовыми Lampa-стриминг, FIFO и downloads.

## Проверки

Запустить make check в чистой подготовленной среде. Выполнить ручные runtime-эксперименты, не вошедшие в автоматизацию, и записать команды/результаты. Первые проверки относятся к будущим A01, A03–A08, A16, A19 и A25, но не закрывают эти составные сценарии целиком.

## Definition of Done

- [ ] Выбраны и записаны точные версии и подтверждён способ установки runtime на x86_64/ARM64.
- [ ] Прототип собирается, устанавливается и включается без изменения исходников Deluge.
- [ ] Подтверждены отменяемое HTTP-чтение, deadlines, read_piece и lifetime alert-буферов.
- [ ] Выбран проверяемый алгоритм снятия QoS и восстановления после save-resume/crash.
- [ ] Зафиксированы mapping v1/v2/hybrid и основные конфликты с пользовательскими действиями.
- [ ] Проверен выбранный потоковый ZIP64 writer.
- [ ] Сохранены версии клиентов, fixtures и минимальный контракт совместимости.
- [ ] Makefile выполняет реальные базовые сценарии; make check и smoke проходят.
- [ ] README содержит воспроизведённые инструкции подготовки, сборки, установки прототипа и тестирования.
- [ ] Создан отчёт с фактами и ограничениями; индекс фаз обновлён.

## Граница перехода

Если ключевая функция требует изменения Deluge либо сохраняет небезопасные overrides, описать конкретное препятствие и вариант решения. Не переходить к полномасштабной реализации с непроверенным предположением и не менять способ поставки молча.
