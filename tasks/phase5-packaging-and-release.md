## Цель

Подготовить первую устанавливаемую версию с подтверждённой совместимостью, понятной документацией и GitHub Actions для автоматической сборки и публикации плагина. Финальная приёмка проверяет весь продукт, включая ресурсные ограничения и обе архитектуры.

## Задачи

### 1. Упаковка и воспроизводимость

- Зафиксировать подтверждённые сочетания Deluge/Python/libtorrent/Twisted и формат устанавливаемых plugin artifacts.
- Проверить сборку из чистого checkout с закреплёнными зависимостями, правильной версией, лицензиями и включением web-ресурсов.
- Подготовить manifest совместимости и SHA-256 checksums. При повторной сборке объяснить возможные различия метаданных; не заявлять побайтовую воспроизводимость без проверки.
- Проверить установку, обновление, отключение и удаление плагина в изолированном профиле, включая миграции и сохранение пользовательских данных.
- Подтвердить runtime на Linux x86_64 и ARM64. Общий Python artifact допустим при доказанной совместимости; копирование одного пакета под разными именами не заменяет запуск на двух архитектурах.

### 2. Docker и Makefile

- Добавить рабочий Docker Compose с Deluge, Web UI и плагином; раздельно указать ports, public_base_url, UID/GID, права и постоянные volumes config/SQLite/downloads.
- Проверить работу обеих архитектур и отсутствие потери политики/данных после пересоздания контейнеров.
- Реализовать make docker-build, docker-up, docker-down и release-check по общему контракту. docker-down не удаляет постоянные volumes.
- release-check проверяет версии, комплект artifacts, manifest, checksums и smoke-установку без публикации в удалённые сервисы.
- Обновить make help и включить в check все обязательные автоматические проверки продукта; тяжёлые нагрузочные сценарии описать отдельными воспроизводимыми командами.

### 3. GitHub Actions: сборка и публикация плагина

- Расширить .github/workflows/checks.yml до подтверждённой матрицы; различать native ARM64 и эмуляцию в результатах.
- Создать .github/workflows/release.yml: версия vX.Y.Z, включая выбранный формат prerelease-тегов, запускает проверки и выпуск именно commit этого тега.
- Переиспользовать checks workflow и Makefile; сверять tag с версией пакета, выполнять build, smoke и release-check до публикации.
- Публиковать в GitHub Releases устанавливаемые plugin artifacts, checksums, manifest совместимости и release notes. Публикация только Docker-образа не выполняет требование.
- Добавить ручной режим проверки pipeline без публикации; в нём получить тот же комплект файлов как workflow artifacts.
- Ограничить права записи стадией публикации; PR/push-проверки не должны публиковать. Не запускать недоверенный PR-код с публикационными правами.
- Не перезаписывать молча уже опубликованные assets другой сборкой той же версии. При ошибке не объявлять неполный комплект готовым релизом.
- Проверить сам workflow: ошибки тестов/несовпадение версии блокируют публикацию, dry run не создаёт release, подготовленный комплект пригоден к установке.
- Реальные GitHub runs и публикацию assets проверить в согласованном тестовом/draft-release сценарии. Создание внешнего репозитория, тега или публичного релиза выполняется в пределах отдельного либо уже предоставленного разрешения пользователя; локальная разработка workflow сама по себе такого разрешения не даёт.

### 4. Итоговая функциональная и ресурсная приёмка

- Выполнить весь набор A01–A26. Собрать сводку: автоматические/ручные проверки, точные версии, архитектуры, результаты и ссылки на доказательства.
- Проверить два playback-потока по 50 Mbit/s в течение 15 минут на стенде из ТЗ, p95 первого байта готового диапазона ≤1 с и p95 задержки reactor ≤100 мс.
- Проверить лимиты payload-буферов, медленных клиентов, большой ZIP без промежуточного архива, 1000 GET/seek/cancel и 20 enable/disable.
- Измерять память libtorrent, RSS процесса и служебные структуры ZIP отдельно. Не выдавать бюджет payload за общий предел памяти Deluge.
- Повторить основные сценарии на выбранном NAS/ARM64, указать модель/среду и рекомендуемые лимиты по результатам. Эмуляция ARM64 не заменяет измерение NAS.
- При недостаточной производительности показать измерения и требуемую корректировку; не ослаблять функциональные требования и не отмечать непройденные критерии выполненными.
- Direct-read оптимизация готового payload учитывает согласованное уточнение §6.2 SPEC: обнаруживать внешнюю запись в содержимое во время передачи не требуется. Native-готовность, safe paths/access/instance, FIFO, lifecycle cancellation и реальные I/O errors остаются обязательными. Реализация и фактические проверки описаны в отчёте; целевая HDD-приёмка остаётся открытой.

### 5. README и документация выпуска

- Довести README до инструкции для нового пользователя: назначение, возможности, требования, таблица версий, получение artifact, установка core/web, конфигурация и Lampa/Num.
- Указать проверенные команды сборки/тестирования из чистого checkout, назначение make-целей, системные prerequisites и результат каждой основной команды.
- Описать Docker, обновление/отключение, backup/restore, диагностику, FIFO и правила file/ZIP; убрать устаревшие пометки «пока не реализовано» только для реально готового.
- Описать triggers CI/release, порядок выпуска версии, получение test artifacts, dry run и восстановление после неудачной публикации.
- Проверить инструкции пошагово в чистом окружении. Ссылки на release и статусы CI должны вести к существующим ресурсам.

## Проверки

Выполнить make check и make release-check для поддерживаемой матрицы, Docker smoke, функциональную и нагрузочную приёмку. Зафиксировать реальные checks/release dry-run runs и результат проверки публикационного сценария. Если GitHub-репозиторий, runner или устройство недоступны, оставить соответствующие DoD открытыми и точно назвать недостающую проверку.

Подготовленный workflow и локальные artifacts не означают, что релиз уже опубликован. Публичный выпуск, если он входит в текущую задачу, выполняется только после готовности и проверки конкретного комплекта.

## Definition of Done

- [x] Поддерживаемая runtime-матрица подтверждена на Linux x86_64/ARM64; пакет устанавливается штатно.
  Локально ARM64 и эмулируемый x86_64; native hosted runners/NAS остаются отдельными gates.
- [x] Docker Compose и make docker-* работают; постоянные данные переживают пересоздание контейнеров.
- [ ] make check/release-check проходят; комплект содержит artifacts, checksums и manifest.
- [ ] checks.yml автоматически проверяет согласованную матрицу, результаты реальных runs сохранены.
- [ ] release.yml собирает и проверяет commit тега, публикует plugin artifacts и поддерживает dry run.
- [ ] Успех и отказ публикационного сценария проверены; статус тестовой/публичной публикации указан отдельно.
- [ ] Все A01–A26 и обязательные ресурсные проверки подтверждены; измерения NAS сохранены.
- [ ] README позволяет установить, настроить, собрать и протестировать проект по проверенным командам.
- [ ] Release notes и инструкции обновления/восстановления соответствуют фактическому продукту.
- [ ] Итоговый отчёт, индекс фаз и общий DoD в ТЗ обновлены без фиктивных отметок.
