# План разработки Deluge Stream Plugin

Основание: [SPEC.md](../SPEC.md), разделы 1–16. Правила выполнения — [AGENTS.md](../AGENTS.md).

Фаза 0 завершена: есть устанавливаемый исследовательский core-прототип, Makefile, v1/v2/hybrid matrix, SIGKILL/identity/worker-result guards, queue/session pause и retained-ownership recovery с commit/crash тестами. Клиентский gate закрыт реальными module-level fixtures Lampa/TorrServer по уточнению пользователя от 29 октября 2026 года; Num и полноценная UI/playback-приёмка отложены. Portability/GC/live QoS не объявлены готовыми исследованиями. См. [отчёт](implementation/phase0-report.md).

## Последовательность и статус

По HTTP-эмуляции `torrent-stream-hub` сохранены source-derived schemas и примеры
с provenance; [контракт и отличия от ТЗ](../docs/torrserver-contract.md).
Сами source-derived примеры не заменяют реальные captures и не добавляют handlers фазы 3.
Дополнительно записаны 35 реальных обменов TorrServer MatriX.147.1 и модуля
Lampa 3.4.4 в Chromium; это согласованный объём клиентского DoD фазы 0.
Num и полноценный playback/UI остаются непроверенными и перенесены в последующую приёмку.

В фазе 1 подготовлены SQLite repository/worker, core/web handshake и диагностическая
страница, workflow checks через make ci-check. Storage подключён к Core, добавлены
policy RPC/status fields и схема настроек; lifecycle/crash проверены. Вместо
hardlink-контракта согласован [сброс связей на явном отключении](../docs/instance-identity-decision.md),
без сброса политики на обычном restart daemon. После crash — подтверждение
администратором перед прежней публикацией и будущей очисткой. Фаза 1 завершена;
результаты и ограничения — в [отчёте](implementation/phase1-report.md).

## Обязательные сквозные результаты

### README

[README.md](../README.md) уже создан как человекочитаемое описание и честный статус проекта. В фазе 0 добавить реальные инструкции подготовки/сборки прототипа; в фазе 1 — установку core и web-частей; в фазах 2–4 — работающие пользовательские сценарии; в фазе 5 — окончательные инструкции релиза, Docker, обновления и диагностики. Каждый DoD содержит проверку актуальности README.

### Makefile

Makefile создан в фазе 0 и расширяется вместе с кодом. Текущий make check проверяет исследовательский прототип и сохранённые контрактные записи, но не подтверждает полную продуктовую приёмку. Не добавлять успешные заглушки для сборки или отсутствующих тестов.

| Цель | Обязательный контракт | Фаза |
| --- | --- | --- |
| help | Безопасная default-цель, команды, переменные и prerequisites | 0 |
| bootstrap | Подготовка изолированного окружения из закреплённых зависимостей; системные prerequisites объясняются отдельно | 0 |
| lint, format-check | Реальные проверки Python/других уже появившихся исходников | 0 |
| check-docs | Синтаксические/структурные проверки Markdown и существующих локальных ссылок | 0 |
| test-unit | Детерминированная чистая логика без публичного swarm | 0 |
| test-integration | Настоящие зависимости в изолированном профиле, локальный seed и явные ошибки отсутствующего runtime | 0 |
| test | Все обязательные автоматические тесты уже реализованных компонентов | 0 |
| build | Сборка plugin artifact в dist/ с версией и совместимостью | 0 |
| smoke | Проверка именно собранного artifact: установка, загрузка, enable/disable | 0 |
| check | check-docs, lint, format-check, test, build и smoke; зависимости не гоняются в неверном порядке | 0 |

Параметры PYTHON, BUILD_DIR, DIST_DIR и путь изолированного test profile должны быть явно описаны. Не переопределять системные HOME/CODEX_HOME для собственных задач. Не требовать записи в профиль реального Deluge для make check.

На каждой фазе make check охватывает то, что уже должно быть реализовано по её DoD. Внутри отдельного сценария допустимы явно помеченные необязательные варианты матрицы, но обязательная проверка не может стать «зелёной» из-за skip.

### GitHub Actions

| Workflow | Когда создаётся | Назначение |
| --- | --- | --- |
| .github/workflows/checks.yml | Фаза 1 | PR/push/ручная проверка, make check, сборка и загрузка тестовых artifacts; возможность вызова из release workflow |
| .github/workflows/release.yml | Фаза 5 | Версионный тег, проверки того же commit, build/smoke/release-check, публикация artifacts в GitHub Releases |

CI расширяется в фазах 2–4, а не откладывается до конца разработки. В фазе 5 подтверждается матрица Linux x86_64/ARM64 и различие между сборкой пакета и запуском runtime на архитектуре. Pure-Python artifact может быть общим, если это доказано; нельзя выдавать одинаковые копии пакета за отдельные native-проверки.

Релизный pipeline должен иметь режим проверки без публикации. Публикация контейнерного образа не заменяет публикацию устанавливаемого плагина и не является обязательной целью первой версии.

## Как читать приёмочные сценарии

Идентификаторы A01–A26 определены в SPEC.md §14. Полный прогон — обязанность фазы 5. В ранних фазах проверяются реализуемые части сценариев и фиксируется покрытие: например, фаза 2 проверяет защиту ZIP через общий lifecycle-тест, а реальный ZIP появляется в фазе 4.

Нельзя закрыть весь составной сценарий по проверке только одной его части. Ручные проверки Lampa/Num и реального NAS отмечаются отдельно от автоматических тестов.
