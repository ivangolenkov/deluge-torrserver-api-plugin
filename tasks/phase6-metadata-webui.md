# Фаза 6: просмотр и редактирование метаданных Lampa в Web UI

Статус: **Завершена**. [Фактический отчёт и границы проверок](implementation/phase6-report.md).

Основание: запрос пользователя от 31 октября 2026 года, [SPEC.md](../SPEC.md),
§§5.3, 9.4, 11. Предпосылки: реализованные хранение metadata и TorrServer API
фазы 3, Web UI фазы 4 и упаковка фазы 5. Перед реализацией прочитать их актуальные
отчёты, в том числе [отчёт предыдущей фазы](implementation/phase5-report.md).
По прямой команде пользователя реализация начата до полного DoD фаз 3 и 5.
Их незакрытые проверки сохраняются и не объявляются выполненными этой фазой.

## Цель и границы

Дать пользователю возможность просматривать и редактировать сохранённые вместе
с торрентом дополнительные поля TorrServer/Lampa: `title`, `poster`, `category`,
`data`, прямо в стандартном Web UI Deluge. Источник истины — существующая запись
SQLite, связанная с `record_id`, а не отдельная копия данных для редактора.

Это не редактор BitTorrent metadata, имён файлов, labels, torrent options,
viewed-меток или всей локальной карточки фильма Lampa. Доступны только переданные
серверу данные. Не добавлять синхронизацию локальной базы Lampa, автоматический
поиск карточек/постеров, массовое редактирование или отдельный сервис.

## Задачи

### 1. Контракт и хранение

- Уточнить по существующим fixtures форму значений Lampa и семантику отсутствующего
  поля, пустой строки и отображаемого fallback-названия. В форме различать реально
  сохранённое значение `title` и имя торрента, подставляемое TorrServer API.
- Сохранить строковый контракт всех четырёх полей. `data` — произвольная строка,
  а не обязательно JSON: исходный текст должен сохраняться без потерь и скрытой
  нормализации. Применять patch только к явно изменённым полям, не удаляя остальные.
- Задать и документировать конечные ограничения размера полей и общего RPC-запроса
  на основе текущих лимитов и fixtures. Проверять их на сервере, включая Unicode;
  превышение отклонять, а не обрезать. Не делать существующие записи нечитаемыми.
- Реализовать атомарную проверку версии metadata при сохранении. Токен меняется
  при любом изменении, включая TorrServer `add/set`, и не допускает незаметного
  возврата к устаревшей форме. Проверка и запись выполняются одной транзакцией.
  Выбрать отдельную ревизию metadata или эквивалентный токен; не связывать конфликт
  с несвязанными обновлениями playback/status. При миграции сохранить старые данные.
- Использовать существующий ограниченный DB worker и lifecycle-согласование;
  не выполнять SQLite или тяжёлый разбор данных в reactor. Редактор не защищает
  временный торрент от FIFO на всё время открытой формы.

### 2. Авторизованный RPC

- Добавить версионированные `get_metadata` и `set_metadata` в namespace `stream`.
  Чтение принимает torrent id и ожидаемый `record_id`, возвращает сохранённые поля
  и токен версии; запись дополнительно принимает ожидаемый токен и patch полей.
  Точные сигнатуры согласовать с действующими conventions API при реализации.
- Проверять owner/admin на core для чтения и изменения; shared-доступ сам по себе
  не даёт доступа к редактору. Проверять экземпляр и права повторно при сохранении.
- Не требовать публикации торрента или доступности HTTP listener для редактора:
  используется авторизованный Deluge RPC, в том числе при раздельных core/web.
- Отвергать неизвестные поля, неверные типы, превышение лимитов и устаревший токен.
  Отдавать стабильные публичные ошибки без SQL, traceback и содержимого `data`.
- При delete/re-add того же hash, удалении, disable или потере core отклонять
  устаревшую запись. Не переносить metadata между экземплярами.
- Возвращать успешный результат только после commit. При storage error сохранять
  прежнюю запись; UI не должен показывать неподтверждённый успех.

### 3. Редактор в Web UI

- Добавить кнопку «Метаданные» во вкладку Stream для одного выбранного торрента.
  Открывать форму с полями «Название», «Постер (URL)», «Категория» и многострочным
  `data`, кнопками «Сохранить» и «Отмена», состояниями загрузки и сохранения.
- Открывать форму с актуальным снимком; не перезаписывать введённый текст фоновым
  polling. Не допускать параллельных сохранений и применения ответа к другому
  выбранному торренту или уже закрытой форме.
- Для `data` предоставить явные действия «Проверить JSON» и «Форматировать JSON».
  Невалидный JSON не запрещает сохранение произвольного текста. Форматирование
  применяется только по запросу пользователя; пустое/неизменённое значение не
  преобразуется автоматически. Предупредить о зависимости Lampa от структуры.
- Показывать конфликт версии без перезаписи новой записи: сохранять локальный
  черновик и предлагать явно перечитать данные с предупреждением о его потере.
  Не добавлять молчаливое слияние или принудительную запись поверх конфликта.
- При отмене не записывать данные; при закрытии изменённой формы предупреждать
  о потере правок. Смена выделения не должна незаметно менять объект открытой формы.
- Выводить поля только как текст. Не вставлять `data` как HTML, не исполнять его
  и не загружать постер автоматически по произвольному URL. Обработать XSS-строки,
  Unicode, большие допустимые значения и ошибки RPC понятными сообщениями.

### 4. Совместимость и документация

- После успешного сохранения TorrServer `get/list` возвращают новые поля в рамках
  прежнего контракта; последующий `set` Lampa остаётся работоспособным. Не обещать
  немедленного обновления уже закэшированной карточки в интерфейсе Lampa.
- Изменение metadata не переименовывает торрент/файлы, не меняет labels/options,
  viewed, публикацию, временность, FIFO, priorities, pause/queue и streaming-state.
- Проверить сохранение после штатного restart daemon. Явный disable по-прежнему
  сбрасывает экземплярные metadata согласно действующему lifecycle-контракту.
- Расширить существующие тесты и make-цели, не дублируя логику в CI YAML.
  Обновить README, описание RPC/хранения и при необходимости миграций.
- После реализации создать `tasks/implementation/phase6-report.md` с фактическими
  результатами, исходным DoD, средой/версиями и ограничениями; обновить индекс фаз.
  Не создавать заранее успешный отчёт и не закрывать прежнюю клиентскую приёмку.

## Проверки

- Unit: валидация типов/полей/размеров, permissions, публичные ошибки и patch.
- Временная SQLite: round-trip Unicode и произвольного `data`, пустые/отсутствующие
  поля, атомарный конфликт двух редакторов и редактора с TorrServer `set/add`,
  отказ commit, миграция и сохранность неизменённых полей.
- Настоящий Deluge и установленный artifact: RPC owner/admin/чужого/shared,
  TorrServer add → RPC read → RPC update → HTTP get/list → HTTP set,
  restart, remove/re-add, отключение плагина и неизменность torrent options/policy.
  HTTP-интеграцию не называть проверкой настоящего интерфейса Lampa.
- Настоящий Chromium: открытие/сохранение/отмена, произвольный текст и JSON,
  конфликт с сохранением черновика, смена выделения, закрытие с pending RPC,
  XSS, ошибки хранения, потеря core и несовместимые версии частей.
- Раздельные deluged/deluge-web без общего диска: чтение и запись через RPC,
  в том числе с отключённым TorrServer HTTP listener.
- Команды: `make check-docs`, `make test-unit`, `make test-persistence`,
  `make test-web`, `make test-web-split` и итоговый `make check` в поддерживаемых
  runtime-профилях. Не повторять весь набор без причины после успешного check;
  точные переменные окружения и команды записать в отчёте.
- Покрыть новый A27; для A14/A15/A23/A24 подтвердить относящиеся к редактору
  части (identity, storage error, права, split Web UI), не объявляя повторную
  полную приёмку этих сценариев. Настоящую Lampa проверять отдельно и честно
  отмечать отсутствие такой проверки, если выполнена только HTTP-интеграция.

## Definition of Done

- [x] В Web UI доступны просмотр и редактирование всех четырёх сохранённых полей.
- [x] Произвольный `data` сохраняется без потерь; JSON-инструменты только явные.
- [x] Core проверяет owner/admin, типы, лимиты, экземпляр и версию metadata.
- [x] Конкурентный `add/set` или второй редактор не теряет изменения молча.
- [x] Ошибка commit, remove/re-add и недоступность core не дают ложного успеха.
- [x] TorrServer читает обновлённую запись; его прежние операции совместимы.
- [x] Restart сохраняет правки; явный disable следует прежнему контракту.
- [x] Не меняются файлы, пользовательские options, политика и streaming-state.
- [x] Chromium и split core/web проверены с установленным artifact; XSS не исполняется.
- [x] Новые проверки входят в существующие make-цели/CI; обязательный make check проходит.
- [x] README, отчёт и индекс обновлены; A27 и связанные части A14/A15/A23/A24
  подтверждены фактическими результатами, ограничения клиентской приёмки указаны.
