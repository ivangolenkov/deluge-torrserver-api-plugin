# Техническое задание: Deluge Stream Plugin

Версия документа: 0.2. Дата: 28 октября 2026 года.

Статус: спецификация первой версии для проектирования и реализации. Документ фиксирует согласованный продуктовый объём; технические значения по умолчанию предложены автором ТЗ и могут уточняться по результатам этапа 0 с записью причины изменения.

## 1. Назначение и согласованные решения

Разработать самостоятельный плагин Deluge, который объединяет обычную фоновую загрузку и сидирование торрентов с просмотром файлов через TorrServer-совместимые приложения, в первую очередь Lampa и Num.

Плагин должен использовать существующую сессию libtorrent в Deluge. Создавать второй торрент-движок или параллельно скачивать те же данные другим клиентом запрещено.

Пользователь подтвердил следующие требования:

| Решение | Требование первой версии |
| --- | --- |
| Поставка | Вся серверная функциональность внутри Python-плагина Deluge, без отдельного Go-сервиса |
| Управление | Настройки и действия в стандартном Web UI Deluge |
| Плееры | Совместимость с Lampa/Num через TorrServer API |
| Хранение | Управление временным и постоянным статусом торрента |
| Индикация | В Web UI видно, что торрент сейчас просматривается через Lampa/Num |
| HTTP-скачивание | Возможность скачать отдельный файл и весь торрент ZIP-архивом |
| Готовность к скачиванию | Отдельный файл доступен после его полной загрузки; ZIP — после загрузки всех содержательных файлов торрента |
| Автоочистка | Только при превышении максимального количества временных торрентов |
| Платформы | Linux x86_64 и ARM64, включая NAS и Docker |

Нехватка свободного места не является основанием для дополнительного автоматического удаления. Ограничение общего размера временных данных в первую версию не входит.

### 1.1. Основные пользовательские сценарии

1. Пользователь задаёт адрес плагина как TorrServer в Lampa/Num, добавляет magnet, выбирает файл и начинает просмотр до окончания загрузки.
2. При перемотке приоритет получают данные около новой позиции. Другой зритель того же торрента продолжает смотреть свою часть файла.
3. При добавлении четвёртого временного торрента с лимитом три удаляется самый старый временный торрент вместе с данными, если он не защищён активной передачей.
4. Пользователь делает временный торрент постоянным или явно переводит постоянный во временный через Web UI.
5. Во время просмотра Web UI показывает состояние «Стриминг» и количество активных воспроизведений.
6. Пользователь скачивает готовый файл или ZIP всего готового торрента через Web UI. Такая передача защищает данные от автоочистки, но не считается просмотром.
7. После перезапуска сохраняются временность, FIFO-порядок и метаданные; устаревшие HTTP-сессии и признаки просмотра не восстанавливаются.

### 1.2. За пределами первой версии

- Отдельный Go-сервис, отдельный веб-интерфейс вместо стандартного Deluge Web UI и обязательная GTK-интеграция.
- Транскодирование, HLS/DASH, перекодирование контейнеров, встроенный браузерный видеоплеер.
- Скачивание незавершённых файлов или незавершённого торрента через действия «Скачать» в Web UI. Потоковое воспроизведение через TorrServer при этом поддерживается.
- ZIP с догрузкой отсутствующих данных, сохранение готовых ZIP на диске, возобновление динамического ZIP по HTTP Range.
- Очистка по TTL, общему объёму, свободному месту, рейтингу или времени последнего просмотра.
- Изменение протокола BitTorrent, собственный piece picker, форк или обязательный monkey patch Deluge/libtorrent.
- Полная совместимость со всеми административными функциями TorrServer и воспроизведение его модели RAM-cache.
- Миграция БД, служебных файлов, fast-resume и storage-формата Torrent-Stream-Hub.
- Обязательная поддержка Windows, macOS и 32-битных ARM.

## 2. Термины, источники истины и границы управления

**Временный торрент** — сохраняемый между перезапусками торрент, разрешённый пользователем или TorrServer add для автоматического удаления при превышении количества. «Временный» не означает хранение только в RAM.

**Постоянный торрент** — торрент, исключённый из автоматической очистки. Ручное удаление в Deluge остаётся доступным.

**Опубликованный торрент** — торрент, доступный через TorrServer-порт. Публикация и временность — отдельные признаки.

**Стрим-сессия** — активная передача медиаданных через TorrServer play/stream. Сервер наблюдает HTTP-чтение плеера, а не достоверную позицию декодирования или факт нахождения человека у экрана.

**Передача** — стрим, preload, скачивание файла или ZIP. Все передачи участвуют в защите от автоочистки; только стримы формируют индикатор просмотра.

**Экземпляр торрента** — конкретное добавление в Deluge. Повторное добавление после удаления с тем же infohash является новым экземпляром.

Источники истины:

- Deluge/libtorrent: наличие торрента, метаданные BitTorrent, состояние загрузки, фактические пути и готовность pieces, пользовательские file priorities, pause/resume, очередь и сидирование.
- SQLite плагина: временность, FIFO-ключ, публикация, дополнительные метаданные TorrServer, настройки плагина и журнал незавершённых операций.
- Память плагина: активные сессии, ожидания pieces, refcount, debounce, временные deadlines и краткоживущие download tickets.

По умолчанию все существовавшие до установки плагина и добавленные обычными средствами Deluge торренты являются постоянными. Они не становятся временными при первом чтении, синхронизации или потере записей плагина.

TorrServer list возвращает только опубликованные торренты. Публикация происходит через успешный TorrServer add или явное действие Web UI «Разрешить доступ через TorrServer». Снятие публикации запрещает новые запросы и корректно завершает связанные передачи; оно не удаляет торрент и не меняет временность.

Повторный TorrServer add уже существующего в Deluge постоянного торрента публикует его и сохраняет постоянство, даже если передано save_to_db=false. Уже существующие данные не перемещаются и не скачиваются заново.

## 3. Платформа и архитектура

### 3.1. Базовая матрица

Целевой стабильный Deluge для первого релиза — 2.2.x. Базовый профиль для проверки: Python 3.11, libtorrent 2.0.x, Linux x86_64/ARM64. Точные patch-версии, зависимости Twisted/setuptools и доступные сборки Python bindings фиксируются на этапе 0 в воспроизводимом окружении. Не заявлять поддержку непроверенных комбинаций и всех будущих Deluge 2.x.

Успешный анализ исходников не заменяет проверку Python bindings и внутренних API в целевом runtime. Обязательный этап 0 проверяет их до разработки всего продукта.

### 3.2. Части одного плагина

- **CorePlugin** загружается в deluged: HTTP-сервер, TorrServer API, lifecycle, FIFO, QoS, чтение данных, SQLite, download tickets, HTTP-скачивание и ZIP.
- **WebUIPlugin** загружается в стандартный deluge-web: настройки, столбцы/состояния, действия, получение ссылок на скачивание через авторизованный RPC.
- **DelugeAdapter** изолирует обращения к Core, TorrentManager, Torrent.handle, EventManager, AlertManager и версии libtorrent.

Предлагаемое разделение исходников: deluge_stream/core.py, adapter.py, lifecycle.py, retention.py, streaming.py, piece_reader.py, downloads.py, archive.py, repository.py, http/, webui.py, data/, tests/.

Названия модулей можно уточнять, но HTTP handlers, архиватор и UI не должны самостоятельно реализовывать правила удаления и временности.

### 3.3. Интеграция с Deluge

1. Торренты добавляются/удаляются через штатные операции Deluge, чтобы сохранялись его состояние, события и resume data.
2. Низкоуровневые streaming-операции выполняются через handle существующего торрента.
3. Обычные lifecycle-события получать через EventManager. Для read_piece и необходимых низкоуровневых уведомлений допускается адаптер к AlertManager.
4. Не вызывать session.pop_alerts() самостоятельно: очередь принадлежит Deluge. Не заменять общий alert mask и не снимать чужие handlers.
5. Не блокировать Twisted reactor сетевым ожиданием, файловым чтением, ZIP-обработкой или SQLite. Для операций ввода-вывода использовать ограниченные очереди и worker-пулы.
6. Доступ к mutable-объектам Deluge и публикация результатов worker-операций выполняются в согласованном контексте reactor.
7. Все операции, callbacks и таймеры проверяют актуальность экземпляра торрента. Callback удалённого экземпляра не влияет на новое добавление того же хеша.
8. Не создавать отдельную libtorrent session. Не менять глобальные лимиты скорости и правила фонового скачивания ради просмотра.

### 3.4. HTTP и удалённый Web UI

CorePlugin открывает собственный настраиваемый HTTP listener. На нём размещаются TorrServer endpoints и защищённые download endpoints плагина. Конфигурация и управляющие действия Web UI выполняются через штатную авторизацию RPC Deluge.

deluged и deluge-web могут находиться в разных процессах, контейнерах или на разных машинах. Файлы читает только core-часть на стороне deluged; WebUIPlugin не требует общего диска с демоном.

Для генерируемых ссылок предусмотрен public_base_url: адрес core HTTP listener, доступный браузеру и плееру. Значение может отличаться от bind-адреса из-за Docker/reverse proxy. Плагин не должен подставлять localhost демона в ссылки удалённому пользователю.

## 4. Временность, постоянство и FIFO-очистка

### 4.1. Добавление и смена статуса

| Операция | Результат |
| --- | --- |
| Новый TorrServer add без save_to_db или с false | Временный, опубликованный |
| Новый TorrServer add с save_to_db=true | Постоянный, опубликованный |
| Добавление через обычный Deluge | Постоянный, не опубликованный автоматически |
| Повторный add временного с false | Тот же временный, FIFO-позиция не меняется |
| Повторный add временного с true | Постоянный, из FIFO исключается |
| Повторный add постоянного с false | Остаётся постоянным |
| Web UI «Сделать постоянным» | Постоянство сохраняется до успешного ответа |
| Web UI «Сделать временным» | Явное включение в автоочистку, новая позиция в конце FIFO |

В UI действие «Сделать временным» поясняет, что последующая автоматическая очистка удалит и скачанные данные. Повторная установка уже действующего статуса идемпотентна. Временный → постоянный → временный получает новый FIFO-ключ.

Смена статуса не перемещает файлы, не меняет выбранные файлы, приоритеты, pause/resume и состояние раздачи. Менять политику удаления и публикацию может владелец торрента либо администратор; право чтения shared-торрента само по себе этого не разрешает. Проверка безопасности удаления должна допускать временный статус.

FIFO определяется сохраняемым монотонным ключом, а не timestamp с точностью до секунды. Лимит max_temporary_torrents — положительное целое, предлагаемый default: 3. Постоянные торренты в счётчик не входят. Ошибочное значение отклоняется без частичного применения конфигурации.

### 4.2. Алгоритм очистки

Очистка запускается после успешного создания нового временного торрента, явного перевода в временный статус, уменьшения лимита, восстановления состояния и освобождения защиты передачи. Фоновый повтор — не чаще одного раза в 5 секунд.

1. Если временных не больше лимита, завершить проход.
2. Выбрать самый старый временный экземпляр.
3. Атомарно относительно начала передачи и смены статуса повторно проверить временность, экземпляр, FIFO-позицию и отсутствие защиты.
4. Если кандидат защищён, завершить проход и оставить временное превышение. Более новые торренты вместо него не удалять.
5. Сохранить намерение удаления, закрыть допуск новых передач и вызвать удаление через Deluge с remove_data=True.
6. Подтвердить результат удаления торрент-записи и данных; завершить запись операции. Принятие асинхронной команды само по себе не считается доказанным удалением файлов.
7. Перейти к следующему кандидату только после успешного завершения предыдущего.

Активный stream, preload, HTTP-download файла, ZIP и debounce защищают торрент. Фоновое скачивание, сидирование и пауза сами по себе защитой не являются.

Неуспешный add не запускает очистку. Ошибка очистки не превращает успешный add в ошибку. Если старейший кандидат не может быть удалён, очередь сохраняется с диагностикой и ограниченным повтором.

### 4.3. Безопасность данных и восстановление

- Новые торренты, добавленные плагином, размещать в отдельных каталогах под настроенным download_root; имя должно различать разные экземпляры/торренты с одинаковыми названиями.
- Для существующих торрентов учитывать актуальные save path, переименования и moves Deluge. Не требовать переноса каталога, если безопасное удаление доказуемо.
- Перед включением временности и удалением проверять пересечения фактических файлов с другими торрентами. При неоднозначном владении или выходе за допустимые пути отклонять временность либо блокировать очистку с причиной.
- Не удалять рекурсивно общий download_root или предполагаемую папку по display name. Симлинки, traversal и общие payload-пути не должны позволять удалить чужие данные.
- Потеря или повреждение SQLite не должна делать все торренты временными. Автоочистка отключается до восстановления; обычная работа Deluge сохраняется.
- Журнал удаления переживает рестарт. При отсутствии torrent handle повтор не должен сводиться к удалению произвольного сохранённого пути: использовать проверяемый план файлов и повторную проверку владения либо оставить операцию на ручное разрешение.
- Внешнее удаление/переименование/перемещение в Deluge обрабатывается событиями и сверкой состояния. Плагин не воскрешает удалённые торренты.

## 5. TorrServer-совместимость

### 5.1. Контракт совместимости

Совместимость проверяется с зафиксированными версиями Lampa, Num и эталонного TorrServer. На этапе 0 записать версии/коммиты, сохранить обезличенные fixtures реальных запросов и ответов. Не объявлять совместимость только по HTTP 200.

Поведение Torrent-Stream-Hub использовать как продуктовый ориентир и источник тестовых сценариев, но его stub-ответы, неточные типы DTO и особенности индексов не переносить без проверки с клиентами.

Внешние TorrServer file id — 1-based. Индексы Deluge/libtorrent остаются внутренними. Обязательна явная таблица соответствия; pad-файлы и служебные записи не показываются пользователю. Для v2/hybrid учитывать реальное отображение файлов и pieces из metadata, а не суммировать размеры отображаемых файлов наивно.

### 5.2. Обязательные endpoints

| Endpoint | Требуемое поведение |
| --- | --- |
| GET /echo | Ответ для определения совместимости; строку версии фиксировать fixtures |
| POST /torrents | add, get, list, set, rem, drop, wipe по правилам ниже |
| POST /torrent/upload | Добавление .torrent multipart; новый upload по умолчанию постоянный |
| GET /playlist | M3U опубликованного торрента |
| GET, HEAD /stream и /stream/{name} | play/stream, stat, preload, m3u; параметры link, index |
| GET, HEAD /play/{hash}/{id} | Алиас потокового воспроизведения с 1-based id |
| POST /cache | Совместимое представление готовых данных и читателей |
| POST /settings | get; set/def как документированный compatibility no-op |
| POST /viewed | Минимальный контракт отметок просмотра, подтверждённый fixtures; не использовать как источник streaming-state |
| OPTIONS для HTTP endpoints | CORS preflight |

Добавление поддерживает magnet, v1 infohash в допустимой текстовой форме, HTTP(S)-ссылку на .torrent и redirect/текстовую ссылку на magnet. v2-only/hybrid поддерживаются в пределах подтверждённой матрицы клиентов; внутри плагина они не должны создавать дубликаты при наличии нескольких hash aliases.

Добавление сериализуется по идентичности торрента. Когда metadata ещё не получены, возвращать определённое состояние ожидания; не блокировать reactor и не выдумывать список файлов.

### 5.3. Действия и метаданные

- add/get/list/stat возвращают совместимые title, name, hash, timestamp, размеры, скорости, состояние и file_stats. title, poster, category, data сохраняются в SQLite.
- set меняет дополнительные метаданные плагина; не переименовывает файлы и не меняет Deluge labels или torrent options без отдельного явного действия.
- rem удаляет опубликованный торрент из Deluge без удаления payload-файлов. Запрос во время активной передачи отклоняется с конфликтом; ручное принудительное удаление через обычный Deluge остаётся отдельной операцией пользователя.
- drop и wipe принимаются как совместимые no-op и не вызывают массового удаления. Закрытие страницы в Lampa не должно удалять торрент.
- settings get отражает используемые параметры совместимости. set/def не меняют реальные настройки Deluge или плагина.
- viewed не должен молча имитировать сохранение, если выбранные клиентские сценарии реально требуют его. На этапе 0 фиксируется минимальный нужный контракт; при наличии add/get/rem метки хранить в SQLite, привязав к файлу и экземпляру.
- Неизвестное действие возвращает определённую ошибку; чувствительные детали внутренних исключений наружу не передаются.

Точные типы stat, полей cache и DTO фиксируются JSON schemas/fixtures до реализации соответствующих handlers. Дополнительные диагностические поля допускаются только при сохранении совместимости.

### 5.4. Preload и cache

Preload догружает начальное окно выбранного файла и при необходимости небольшой хвост для метаданных контейнера. Это disk-backed загрузка через libtorrent, без постоянного RAM-хранилища контента.

Повторный preload того же файла объединяется с существующей задачей. Число задач, ожидание и размер окна ограничены; задача не продлевается бесконечно повторными stat-запросами. Сначала получить защиту экземпляра и зарезервировать ресурсы, затем запускать работу; ограничение или ошибка не оставляют refcount.

preloaded_bytes и Filled отражают фактически готовые проверенные байты нужного окна, включая непрерывность от требуемой позиции. Общий процент готовности торрента не заменяет готовность окна. Capacity обозначает логическое окно предзагрузки, а не реально выделенную RAM.

stat/cache/settings/playlist/echo и HEAD не создают playback-сессию, не повышают приоритеты и не продлевают debounce.

## 6. HTTP-стриминг и чтение данных

### 6.1. HTTP-контракт

- GET без Range возвращает 200 и содержимое файла от начала.
- Один корректный bytes-range поддерживает start-end, start- и -suffix; ответ 206 содержит правильные Content-Range и Content-Length.
- Неудовлетворимый byte range возвращает 416 с Content-Range: bytes */<size>.
- Некорректный синтаксис bytes-range возвращает 400. Неизвестная единица диапазона и корректный multi-range в первой версии игнорируются с обычным 200; multipart/byteranges не заявляется. Эта политика фиксируется тестами и проверяется на целевых плеерах.
- HEAD возвращает описание файла без тела, чтения payload и запуска скачивания; Range у HEAD игнорируется.
- MIME определяется по файлу; Accept-Ranges: bytes обязателен для файла. Для playback нет принудительного Content-Disposition: attachment.
- Поддержать необходимые DLNA-заголовки, включая transferMode.dlna.org и запрошенный contentFeatures.dlna.org.
- Нулевой файл, последний короткий piece, границы соседних файлов и файлы более 4 GiB должны обрабатываться корректно.
- До отправки тела ошибки имеют явный HTTP-статус; после начала тела при невосстановимой ошибке закрыть передачу. Нельзя дописывать JSON-ошибку в видеопоток.

### 6.2. Reader

Предпочтительный базовый путь чтения незавершённого файла: ожидание готовности piece и read_piece/read_piece_alert существующей libtorrent session. Не читать незагруженные области sparse/preallocated-файла как готовые нули.

Ожидание выполняется асинхронно, с deadline, отменой при закрытии HTTP-клиента и проверкой экземпляра торрента. Одна операция чтения piece может обслуживать нескольких ожидающих клиентов. Lifetime буфера alert должен быть подтверждён для поддерживаемой Python binding; не удерживать недействительные ссылки после обработки alerts.

Передача учитывает backpressure: если клиент перестал принимать данные, ограничить read-ahead, количество read_piece и очередь готовых буферов. Не читать заранее весь фильм и не накапливать данные в списке Python-объектов.

Готовые файлы допустимо читать напрямую с диска как оптимизацию. Перед этим подтвердить готовность, текущий путь, отсутствие recheck/move/error и корректность открытия. Процент 100%, один stat() или историческая запись SQLite недостаточны. Прямая передача также получает общую защиту от автоочистки.

Нельзя отдавать файл по произвольному пути из URL. Источник разрешается только по torrent identity и file id через metadata и текущий путь Deluge.

### 6.3. Взаимодействие с пользовательскими настройками

- Ручная пауза торрента или всей сессии не снимается автоматически ради просмотра. Готовый читаемый файл может передаваться; запрос недостающих данных получает понятное состояние blocked/conflict.
- Для файла, помеченного пользователем «Не скачивать», первая версия не меняет выбор файлов автоматически. Неготовый файл требует явного включения загрузки в Deluge; уже готовый файл может читаться после проверки доступности.
- Очередь и пользовательские лимиты Deluge сохраняются. Если торрент не допущен к загрузке очередью, плагин показывает причину ожидания; глобальный force-start ради просмотра не выполняется.
- Нехватка места и ошибки записи отражаются в статусе. Новые операции, которым нужны недостающие данные, завершаются определённой ошибкой; готовые читаемые данные допускаются. Плагин не удаляет дополнительные торренты ради освобождения места и не очищает ошибки Deluge автоматически.

## 7. Streaming QoS

### 7.1. Окно загрузки

Для каждой playback-сессии учитывать file id, начало и конец Range, текущую позицию HTTP-чтения, поколение торрента, активность и время последнего продвижения.

Окно приоритета обновляется по мере чтения в рамках одного длинного GET, а не только при новом HTTP Range. Продвижение ограничивается фактической передачей клиенту и небольшим разрешённым буфером.

Предлагаемые начальные значения:

- стартовая предзагрузка — 20 MiB;
- рабочее окно впереди чтения — 20 MiB;
- запас позади позиции — не более двух pieces;
- хвост для MP4/MOV и подтверждённых контейнеров — до четырёх pieces;
- пересчёт — при переходе границы piece или существенном изменении окна, с объединением частых событий.

Это объём данных, которым задаётся срочность, а не обязательный размер RAM-буфера. Размер окна ограничивается границами файла и оставшейся частью запроса; запрос одного байта не должен догружать целиком файл. Политика стартового/хвостового preload не повторяется без необходимости при каждой перемотке.

### 7.2. Приоритеты и несколько клиентов

Для текущего окна использовать time-critical deadlines libtorrent. Piece priorities применяются лишь там, где нужны и где доказано корректное восстановление. Sequential download сам по себе не считается реализацией streaming QoS.

Для piece, необходимого нескольким сессиям, учитывать максимальную требуемую приоритетность и ближайший deadline. Завершение одной сессии не снимает потребность другой. Отдельно проверяются разные файлы, разделяющие граничный piece.

Фоновая загрузка вне окон продолжается по базовым приоритетам пользователя. Не отключать остальные торренты, не изменять глобальные скорости и не переводить весь файл в постоянный High ради локального окна.

Для конкурирующих загрузок внутри одной сессии Deluge сохраняются общие лимиты и очередь. Первая версия не обещает гарантированной полосы для просмотра при насыщении канала другими торрентами; приёмочные тесты должны включать фоновую нагрузку и фиксировать фактическое влияние.

### 7.3. Refcount, debounce и восстановление

Каждый GET playback регистрирует сессию до доступа к данным и освобождает её ровно один раз. При завершении последнего playback запроса сохраняется 10-секундное debounce-окно с защитой от автоочистки. Повторное чтение актуального экземпляра использует общую координацию; старый таймер не должен снять новые приоритеты.

Preload имеет собственный ограниченный lifetime и refcount. Скачивание готовых файлов/ZIP не создаёт deadlines и не включает streaming QoS.

После завершения всех потребностей снять только принадлежащие плагину deadlines/overrides. Восстанавливать актуальные пользовательские настройки, а не слепо применять снимок начала просмотра: пользователь мог поменять file priorities или first/last mode во время стрима.

Плагин должен согласоваться со штатным пересчётом приоритетов Deluge. Общий reset всех deadlines или всех piece priorities без учёта владельцев недопустим. Одновременная работа с другим плагином, независимо управляющим deadlines тех же торрентов, не заявляется совместимой без отдельного теста.

На этапе 0 обязательно проверить, какие временные изменения попадают в resume data. Временный QoS не должен становиться постоянным после disable, штатного рестарта или восстановления после crash. Если выбранный способ оставляет сохраняемые overrides, необходим журнал восстановления и доказанный алгоритм очистки; предпочтителен способ без сохраняемых overrides. Нельзя считать, что восстановление SQLite автоматически исправляет libtorrent resume data.

## 8. Скачивание файла и ZIP из Web UI

### 8.1. Общие правила

Доступ предоставляется только авторизованному пользователю Web UI с правом доступа к выбранному торренту. Для скачивания не требуется публикация торрента через TorrServer.

WebUIPlugin запрашивает у CorePlugin краткоживущий ticket. Ticket ограничен пользователем, текущим экземпляром торрента, режимом file/zip и при необходимости file id. HTTP listener проверяет ticket до открытия файла и регистрации передачи.

Не передавать пароль Deluge или постоянный административный токен в URL. Download tickets исключить из логов. CORS TorrServer не заменяет авторизацию download endpoints. Ticket имеет криптографически случайное значение, проверяется на стороне core и не сохраняется между перезапусками.

Подготовка ticket атомарно согласуется с FIFO: предусмотреть короткую защиту до начала GET, иначе торрент может быть удалён между нажатием кнопки и открытием ссылки. Неиспользованная защита истекает, по умолчанию через 60 секунд; число таких резервов ограничено. HEAD не создаёт новую долгоживущую защиту.

При старте GET резерв преобразуется в активную передачу. Истечение времени выдачи ticket не прерывает уже начатую передачу. Разрешённые повторные Range-запросы ограничены lifetime и числом соединений; после истечения пользователь получает новую ссылку через Web UI.

Браузер скачивает бинарные данные напрямую с core HTTP listener. Передача видео/ZIP через JSON-RPC, Base64, Blob всего файла в памяти браузера или deluge-web запрещена.

### 8.2. Отдельный файл

- Действие «Скачать файл» доступно для выбранного файла, если все его содержательные байты загружены и проверены.
- Не требовать готовности остальных файлов торрента.
- Проверять готовность повторно на сервере; UI не является доказательством готовности.
- Ответ содержит безопасный Content-Disposition: attachment с поддержкой UTF-8 filename, корректный MIME, размер и byte ranges.
- Поддержать возобновление внутри действующего download ticket. Размер и идентичность файла не меняются между частями одной передачи.
- Если файл не готов, вернуть 409 с кодом file_not_ready. Никаких новых download priorities или догрузки от этого действия не возникает.

### 8.3. Весь торрент ZIP-архивом

«Весь торрент» означает все обычные payload-файлы из metadata, включая нулевые файлы. Pad-файлы, .torrent, fastresume, SQLite и другие служебные файлы в архив не входят.

Если хотя бы один payload-файл не готов, ZIP недоступен, даже когда Deluge показывает 100% выбранных файлов. Пропущенный пользователем, но не загруженный файл также делает весь ZIP неготовым. Сервер возвращает 409 с кодом torrent_not_ready и краткой диагностикой; не догружает пропущенные файлы.

Архив формируется последовательно в HTTP-ответе:

- ZIP64 обязателен для больших файлов/архивов и большого числа записей.
- По умолчанию использовать ZIP_STORED: медиафайлы не перекомпрессируются.
- Не создавать промежуточный полный ZIP на диске и не хранить весь архив в RAM.
- Разрешён ограниченный буфер полезных данных и ограниченные метаданные каталога ZIP; предел числа файлов валидируется до старта.
- Сохранять относительную структуру каталога и имена. Нормализовать разделители; запретить абсолютные пути, traversal, symlink escape и неоднозначные/дублирующиеся нормализованные записи.
- Архиву назначать безопасное имя на основе имени торрента. Не включать абсолютные пути NAS.
- Использовать backpressure; отмена загрузки останавливает чтение и освобождает ресурсы.
- Range для динамического ZIP игнорируется, ответ 200; Accept-Ranges: none. Возобновление ZIP не поддерживается в первой версии.
- Content-Length допускается не указывать: поток выдаётся средствами HTTP-сервера без предварительного полного чтения. HEAD не строит архив и не запускает чтение содержимого.

Перед началом проверить весь набор файлов. На время передачи защита охватывает торрент целиком. При ручном удалении, recheck, move или изменении исходных файлов архиватор останавливает передачу; недостающие файлы не пропускаются молча. После отправки части архива корректно завершить его при такой ошибке может быть невозможно — сервер фиксирует причину и прерывает ответ.

### 8.4. Влияние на остальные операции

Download и ZIP не повышают download priorities и не показываются как «Стриминг». В Web UI отображать их отдельными счётчиками «Скачивание файла» / «Скачивание ZIP» и причиной защиты от автоочистки.

Ручное удаление через стандартный Deluge может прервать передачу и должно быть обработано корректно. Защита гарантирует отсутствие автоматического удаления плагином, но не отменяет явные действия пользователя в Deluge или внешнее удаление файлов.

## 9. Web UI и модель состояния

### 9.1. Представление торрента

В стандартном списке/панели торрентов добавить:

- признак «Временный» / «Постоянный»;
- признак публикации через TorrServer;
- состояние «Стриминг» и число активных playback HTTP-запросов;
- отдельные состояния preload, скачивания файлов и ZIP;
- защиту от очистки и причину: playback, preload, file download, ZIP, ticket reservation, debounce;
- для временного торрента — место в FIFO и диагностическую причину отложенной очистки/ошибки.

Streaming-state — дополнительное состояние плагина. Не заменять им штатные Deluge Downloading, Seeding, Paused, Error и не менять их значения.

Индикация:

| Ситуация | Отображение |
| --- | --- |
| Есть активный playback GET | «Стриминг», active_stream_requests > 0 |
| GET завершён, debounce ещё действует | «Ожидание продолжения», active_stream_requests = 0, streaming_protected = true |
| Только preload | «Предзагрузка», без «Стриминг» |
| Только HTTP-file/ZIP | Отдельное состояние скачивания, без «Стриминг» |
| Только stat/cache/HEAD или фоновая загрузка | Просмотр не отображается |

Счётчик HTTP-запросов не подписывать как точное число людей/устройств: один плеер может иметь несколько соединений. Если плеер долго воспроизводит локальный буфер без HTTP-запросов, достоверно определить продолжающийся просмотр невозможно; UI отражает наблюдаемую активность и debounce.

Обновление состояния — через существующий механизм Web UI/RPC/status fields; собственный SSE-сервер не обязателен. На локальном стенде активность должна появляться в UI не позднее двух секунд после получения обновления от core.

### 9.2. Действия

- «Сделать постоянным» и «Сделать временным», включая несколько выбранных торрентов.
- «Разрешить/закрыть доступ через TorrServer».
- «Скачать файл» в Content-панели и «Скачать торрент ZIP» в контекстном меню торрента.
- «Скопировать ссылку воспроизведения» для опубликованного файла.
- Просмотр причины блокировки/ошибки вместо молча неработающей кнопки.

Сервер повторно проверяет права, экземпляр, состояние и готовность. Смена статуса отображается после успешного сохранения; при ошибке прежнее состояние остаётся. В пакетной операции возвращается результат по каждому торренту; частичный успех не скрывается.

Если core-плагин недоступен или версии частей несовместимы, штатный Web UI продолжает работать; действия плагина показывают понятную причину недоступности.

### 9.3. Предлагаемые RPC-методы

| Метод namespace stream | Назначение |
| --- | --- |
| get_config / set_config | Настройки плагина, изменение только администратором |
| get_status | Дополнительные состояния доступных пользователю торрентов |
| set_retention | Смена временности с проверкой экземпляра и прав |
| set_published | Публикация/снятие публикации для TorrServer |

Конкретные имена методов могут уточняться до реализации UI. Внешний контракт должен быть версионирован; запрещено возвращать бинарные payload-данные из этих методов.

| preload_timeout_seconds | 60 | Задача обязательно освобождает защиту |
| download_ticket_start_ttl_seconds | 60 | Время до начала передачи |
| max_pending_download_tickets | 32 | Неограниченная блокировка FIFO tickets запрещена |
| cleanup_retry_seconds | 5 | Без немедленного бесконечного retry |
| max_torrent_upload_mib | 16 | Предел .torrent и скачиваемых метаданных |
| max_json_body_mib | 1 | Для управляющих JSON-запросов |
| max_zip_entries | 100000 | Ограничивает каталог ZIP и подготовку |

Размеры и timeout должны валидироваться до применения. Изменение bind-адреса/порта выполняется контролируемым перезапуском listener; активные запросы получают корректное завершение. Остальные изменения не требуют рестарта deluged, если это не обусловлено конкретной зависимостью и явно не указано в UI.

64 MiB — бюджет плагинных payload-буферов, а не ограничение RSS всего Deluge или памяти libtorrent. Учитывать копии Python bytes, ожидающие read_piece, очереди HTTP и ZIP. При нехватке бюджета приостанавливать дополнительное чтение или отклонять новую передачу; не превышать предел молча. Если размер одного piece не помещается, вернуть явную ошибку ресурсов с рекомендацией настройки, пока не реализован проверенный альтернативный путь чтения.

### 10.2. Доступ и ошибки

- TorrServer listener предназначен для доверенной LAN, работает в заданном владельцем контексте и видит только опубликованные торренты этого контекста. Полноценный multi-user TorrServer в первую версию не входит.
- TorrServer endpoints разрешают CORS origin *, методы GET/HEAD/POST/OPTIONS и необходимые Range/Content-Type/DLNA headers. Credentialed wildcard CORS не включается.
- Web UI использует штатную аутентификацию Deluge. Административные RPC не публикуются как незащищённые HTTP endpoints.
- Download ticket не даёт права изменять настройки или читать другие торренты/файлы. Проверять отзыв доступа и удаление экземпляра.
- Права владельца/shared torrents Deluge учитываются на RPC и повторно при выдаче данных. Клиентский torrent_id не является разрешением на доступ.
- Прокси-заголовки учитывать только от настроенного trusted proxy. Не строить публичные ссылки из непроверенного Host при наличии public_base_url.
- Для HTTP(S) источников .torrent/magnet ограничить число редиректов, время, размер и число параллельных запросов. Не разрешать file:// и произвольные локальные пути. Доступ к LAN-источникам допустим в принятой модели локального сервера.

Собственные download endpoints и RPC возвращают стабильные машинные коды ошибок: torrent_not_found, file_not_ready, torrent_not_ready, torrent_paused, metadata_pending, storage_error, disk_full, operation_conflict, transfer_limit, ticket_invalid, incompatible_runtime. Для TorrServer формат ошибок согласуется с fixtures.

Предлагаемое HTTP-отображение: 400 — некорректный запрос, 401/403 — доступ, 404 — отсутствие, 409 — конфликт/неготовность, 413 — превышенный размер входных данных, 416 — неудовлетворимый Range, 429 — лимит передач, 503 — временная недоступность/ресурсы, 504 — ожидание без прогресса. При подтверждённом ENOSPC допускается 507 до начала тела. Не менять статус после начала binary response.

## 11. SQLite и согласование состояния

SQLite плагина находится в каталоге конфигурации Deluge и сохраняется независимо от package-файла. Обязателен WAL, настройка busy timeout и ограниченное число соединений. Соединения используются в соответствии с потоковой моделью; длительная блокировка БД не останавливает reactor.

Минимальные логические сущности:

| Сущность | Основные данные |
| --- | --- |
| torrent_policy | record_id, Deluge torrent id, hash aliases, owner, is_temporary, fifo_sequence, published, timestamps |
| torrent_metadata | title, poster, category, data; привязка к record_id |
| operation_journal | add/remove/смена политики, стадия, проверенные идентификаторы и ошибка |
| viewed | Минимальные отметки просмотра, если нужны зафиксированным клиентским сценариям |
| settings/schema_version | Версия схемы и настройки плагина |

Битовые карты готовности, payload, peer-state и копия resume data в SQLite не сохраняются. Допустим только краткоживущий кэш статуса, не используемый как доказательство готовности.

Операции SQLite и Deluge не образуют единую транзакцию. Для добавления, смены политики и удаления определить recoverable последовательность с журналом, идемпотентностью и сверкой при старте. После сбоя нельзя назначать новую временность давно существовавшему постоянному торренту, дублировать add или переиспользовать старую FIFO-позицию удалённого экземпляра.

Запись is_temporary обновляется отдельной командой. Периодическая синхронизация статуса не должна перезаписывать её значением по умолчанию или воскрешать удалённые записи.

Миграции выполняются последовательно. Неизвестная более новая схема не открывается для записи. Ошибка миграции выключает функции плагина, требующие записи, с диагностикой, сохраняя работоспособность самого Deluge.

## 12. Жизненный цикл, отмена и наблюдаемость

### 12.1. Включение и выключение

При enable: проверить runtime, открыть/мигрировать БД, согласовать записи с загруженными торрентами, зарегистрировать handlers/RPC/status fields, затем открыть HTTP listener и фоновые задачи. Не запускать очистку до окончания восстановления каталога Deluge.

При disable: прекратить приём новых запросов и выдачу tickets, отменить ожидания, корректно остановить передачи, снять принадлежащие плагину временные приоритеты/deadlines, остановить listener/таймеры, снять handlers/status fields и закрыть БД. Не удалять payload и не останавливать сам Deluge.

Повторные enable/disable не создают дублирующиеся listeners, handlers, фоновые задачи или записи в UI. При частичном отказе enable выполнить обратимое освобождение уже созданных ресурсов.

При рестарте/crash: runtime-сессии и tickets недействительны. После согласования resume data и каталога возобновить обычную работу и FIFO. Внешнее изменение файла/торрента отменяет устаревшие чтения и reservations.

### 12.2. Логи и диагностика

Логировать через механизм Deluge: начало/окончание передачи, тип stream/file/zip/preload, hash/record_id, file id, Range, причину завершения, первый байт, объём и длительность; смену политики, попытку/отсрочку/результат очистки и восстановление после сбоя.

Не логировать download tickets, пароли, URL query с секретами трекеров/источников и содержимое пользовательского data. Частые ошибки ограничиваются по частоте без потери итоговой причины.

Диагностика должна показывать текущую версию Deluge/Python/libtorrent, число каждого типа передач, число ожиданий pieces, объём payload-буферов, длину FIFO, превышение лимита, причины защиты, последние ошибки и задержку reactor.

## 14. Тестирование и критерии приёмки

### 14.2. Ресурсы и производительность

Предлагаемый воспроизводимый стенд: Linux, 4 vCPU, 4 GiB RAM, SSD, локальный seed, сеть без ограничения ниже 1 Gbit/s. Точные параметры и версии публикуются в отчёте. Отдельно измерить целевой NAS/ARM64; конкретную модель устройства выбрать перед нагрузочной приёмкой.

Цели первой версии на воспроизводимом стенде:

- Два параллельных playback-потока по 50 Mbit/s в течение 15 минут без ошибок данных и неограниченного роста буферов при достаточной скорости seed.
- Для уже готового диапазона p95 времени до первого байта не более 1 секунды; для недостающего диапазона гарантируется корректное ожидание и приоритет, но не время получения из произвольного swarm.
- p95 задержки reactor не более 100 мс при указанной нагрузке; медленные операции не выполняются в callback целиком.
- Payload-буферы остаются в настроенном бюджете. RSS Deluge, память libtorrent и служебные структуры ZIP измеряются отдельно, без ложного обещания общего лимита 64 MiB.
- После 1000 коротких GET/seek/cancel и 20 циклов enable/disable число живых сессий, ожиданий и файловых дескрипторов возвращается к исходному уровню с учётом документированного кэша.
- Большой ZIP передаётся без временного архива на диске; потребление payload-памяти не растёт пропорционально размеру контента.

Если целевой NAS не достигает предлагаемых скоростей, отчёт должен показать измерения и рекомендуемые лимиты. Пересмотр чисел не отменяет функциональные требования, корректность данных и ограниченность ресурсов.

## 16. Общий Definition of Done первой версии

- [ ] Вся серверная функциональность поставляется как плагин Deluge без Go-сервиса и без патчей Deluge/libtorrent.
- [ ] Подтверждены Linux x86_64 и ARM64 и опубликована точная runtime-матрица.
- [ ] Lampa и Num работают через зафиксированный TorrServer-контракт: add, файлы, preload, play, Range и seek.
- [ ] Streaming QoS следует текущей позиции HTTP-чтения и корректно обслуживает несколько клиентов.
- [ ] Пользовательские priorities/pause/queue не теряются после просмотра, disable или восстановления.
- [ ] Временность меняется в обе стороны и сохраняется; постоянные торренты не удаляются автоматически.
- [ ] FIFO-очистка запускается только из-за превышения количества и уважает все активные передачи/debounce.
- [ ] Web UI показывает временность, публикацию, наблюдаемый стриминг и отдельные file/ZIP передачи.
- [ ] Готовый отдельный файл скачивается с Range и корректным именем; неготовый отклоняется без догрузки.
- [ ] Весь готовый торрент скачивается ZIP64-архивом с правильным составом и без промежуточного полного архива.
- [ ] Пропущенные недогруженные файлы блокируют ZIP даже при 100% wanted-progress Deluge.
- [ ] Авторизация RPC/tickets работает, чужие и неопубликованные данные не выдаются через TorrServer.
- [ ] Crash/restart, конкурентное удаление/закрепление/чтение, disk errors и отмена передач покрыты проверками.
- [ ] Есть воспроизводимые тесты, результаты нагрузки, инструкции установки и итоговый отчёт.
- [ ] Человекочитаемый README содержит проверенные инструкции установки, настройки, сборки и тестирования.
- [ ] Makefile выполняет основные сценарии build/test/check/smoke, Docker и release-check без успешных заглушек.
- [ ] GitHub Actions автоматизирует проверки, сборку и публикацию plugin artifacts; CI и release pipeline фактически проверены.
