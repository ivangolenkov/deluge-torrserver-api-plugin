# Идентичность экземпляров: согласованный lifecycle и история решения

Статус: **первоначальное предложение hardlink-контракта заменено согласованным
упрощением**, 29 октября 2026 года. Ниже сохранены исследование и прежнее
предложение для истории, а не как действующее обязательное требование.

## Принятое упрощение

Пользователь разрешил считать торренты постоянными после явного отключения
плагина и отдельно подтвердил сброс публикации и экземплярных metadata/viewed.
После повторного включения создаются новые постоянные неопубликованные связи.
При этом штатный restart deluged и crash **не являются** явным отключением:
сохранённые временность/FIFO не сбрасываются только из-за перезапуска.

Для политики не вводятся hardlinks, ограничения config-ФС или перенос
исследовательского QoS witness в production. Живые remove/re-add различаются
новыми record_id и событиями; обычный native restore сохраняет связи SQLite.
Порядок между Deluge и SQLite всё ещё не является общей транзакцией: отдельно
проверяется crash между native remove/re-add и commit наблюдателя SQLite.
Упрощение не разрешает небезопасно наследовать старые разрешения в таком окне.

После воспроизведения этого окна реальным SQLite writer-lock и SIGKILL пользователь
выбрал **подтверждение после crash**: сохранить временность/FIFO, но заблокировать
автоочистку и прежнюю публикацию до решения администратора. Подтверждение связано
с актуальным каталогом; marker сохраняется в БД. Это действующее согласованное
решение, в отличие от исторического предложения hardlinks ниже. Штатный stop/start
daemon marker не устанавливает, явное отключение плагина сбрасывает связи.

## Почему нельзя безопасно подключить политику только по данным Deluge

SPEC §§2, 3.3, 4.3 и 11 одновременно требует сохранять временность после рестарта
и не наследовать её новому экземпляру того же infohash. При этом пользователь
может удалить и повторно добавить торрент, пока плагин выключен. In-memory UUID
и EventManager помогают во время работы плагина, но не закрывают этот разрыв.

В установленном Deluge 2.2.0 просмотрены TorrentState, TorrentManager.create_state,
_save_state, _add_torrent_obj, on_alert_save_resume_data и Torrent.write_torrentfile.
Штатный TorrentState заново собирается из фиксированных native-полей; добавить
атрибут к Python-объекту недостаточно для его сохранения. В подтверждённом binding
libtorrent 2.0.8.0 add_torrent_params содержит added_time, но не uuid/userdata.
Неизвестные ключи fastresume не являются подтверждённым сохраняемым каналом:
Deluge кодирует его заново из native params.

Выполнен **реальный** контрольный эксперимент `tools/probe_instance_identity.py`:
один одноразовый профиль, paused torrent, remove_data=False, тот же filedump,
filename и save path; затем повторный add. На ARM64 и эмулируемом x86_64:

| Проверка | ARM64 | x86_64 |
| --- | --- | --- |
| Разные живые Torrent-объекты | true | true |
| Тот же infohash | true | true |
| Одинаковые все поля сохраняемого TorrentState | true | true |
| Одинаковый native added_time | true | true |
| Native added_time в успешной паре | 1793264992 | 1793264993 |

Это доказательство недостаточности **этой комбинации признаков**, а не
доказательство невозможности любого другого identity-протокола. На каждой
архитектуре коллизия наблюдалась в первой паре. Нет публичного swarm, плагин
не включается, чужой профиль не открывается; посторонний sentinel payload
сохранён. После опыта Deluge штатно останавливается, удаляется только одноразовый
каталог самого опыта. Проверяется снимок create_state, не полноценный offline
restart/reconciliation. Не выдаём его за готовую продуктовую защиту.

Команды:

```sh
docker run --rm --platform linux/arm64 --network none -v "$PWD:/work" deluge-stream-phase0:arm64 python -I tools/probe_instance_identity.py
docker run --rm --platform linux/amd64 --network none -v "$PWD:/work" deluge-stream-phase0:amd64 python -I tools/probe_instance_identity.py
```

Нельзя использовать сохраняемые filename/name/owner/trackers как скрытое хранилище
UUID без побочных эффектов: например, filename используется для фильтрации и
копирования/удаления копий torrent-файла. Не предлагаются форк или monkey patch
сериализации Deluge. Hash пути, имя payload и время с точностью до секунды не
становятся разрешением на наследование временности или восстановление QoS.

## Историческое предложение hardlink-контракта (не принято)

1. Ввести capability-контракт **только для каталога конфигурации deluged**:
   поддерживаются hardlinks на обычные служебные файлы внутри одного filesystem
   и проверяемые inode/fingerprint-признаки. Это не требование к диску downloads.
2. Доработать исследованный metadata-witness фазы 0: сохранить UUID record_id,
   pin служебного `.torrent` и fingerprint до выдачи разрешения на временность.
   Связывание и файловый I/O выполняются worker-очередью, не reactor.
3. При неподдерживаемой ФС или недоказанной идентичности **не включать опасные
   операции**: временный режим/автоочистка и применение старых QoS overrides
   недоступны с причиной identity_unproven. Обычный Deluge остаётся работоспособным.
   Сохранённые policy-записи не удаляются и не превращаются молча в постоянные.
4. После backup/restore или замены metadata не считать старый witness валидным
   по одному hash. Консервативно остановить опасные операции; процедуру явного
   восстановления описать и проверить отдельно. Поддержка произвольного NAS/backup
   не объявляется по успешному overlayfs-эксперименту.
5. Добавить продуктовые restart/crash/offline delete-readd и unlink-fault проверки,
   bounded retirement/GC только своих служебных ссылок и конфигурационную диагностику.
   Payload не связывается, не переименовывается и не удаляется этим механизмом.

Прототип уже проверял hardlink witness на overlayfs и отказ при offline re-add
и неудачном удалении старой metadata. Это основание для дальнейшей реализации,
не готовый переносимый провайдер. Решение потребует уточнить SPEC/план и README
о capability-контракте; оно **ещё не принято**. Обязательное hardlink-требование
не было согласовано ранее и не вводится этим документом автоматически.

Альтернатива — продолжить поиск другого сохраняемого identity-канала без такого
FS-контракта. До его подтверждения соответствующие DoD фазы 1 остаются открытыми.
Ослаблять защиту до hash/added_time или сбрасывать временность на каждом рестарте
не предлагается: это нарушает согласованный продуктовый контракт.
